6.【The latest from GitHub's engineering team - The GitHub Blog】GitHub 打造 Agent Host Protocol,讓 agent 工作階段可跨裝置接續
[2026-11-17] · The latest from GitHub's engineering team - The GitHub Blog
GitHub 工程團隊發表文章,說明他們打造的開放協定「Agent Host Protocol」,目的是讓 AI coding agent 的工作階段(session)能在不同編輯器、應用程式、手機與雲端之間無縫延續。文章指出,過去 agent 的執行狀態通常被綁死在單一應用程式或裝置上,一旦切換環境,先前的對話紀錄與任務脈絡就會遺失。Agent Host Protocol 把「session」抽象成一個可攜物件,讓使用者可以在手機上啟動任務、回到編輯器繼續查看進度,甚至交接給雲端代理執行。⚠️ 本文發布於 2026-11-17,並非今日(2026-11-18)文章,但仍在近 7 日內,屬於近期而非今天的重點。
新舊比較：
  • 先前：AI coding agent 的工作階段通常綁定在單一編輯器、應用程式或裝置上,切換裝置或工具就會中斷脈絡與歷史紀錄
  • 新在哪：GitHub 設計並開放 Agent Host Protocol,把 agent session 抽象成可攜式物件,定義跨編輯器、App、手機與雲端的共同存取介面
  • 解決了什麼：讓使用者的 agent 任務與對話脈絡能在裝置與工具之間接續,不必重新說明需求,也讓各家工具不必各自重造 session 管理機制
7.【The Cloudflare Blog】Cloudflare 將 Clairic 與新版 Clairic-flash 以 open-weight 形式釋出
[2026-11-18] · The Cloudflare Blog
Cloudflare 宣布旗下的資訊擷取(extraction)模型 Clairic 正式從 preview 階段畢業,同時推出更輕量的 Clairic-flash,兩者都以 open-weight 形式在 Workers AI 上開放,公告來自 Cloudflare 新成立的「Workers AI Superintelligence team」。這顯示公司持續投入自有模型研發,而非完全依賴第三方供應商的模型。Open-weight 代表開發者可以直接下載權重、在地端或自架環境中檢視、微調或部署這兩個模型,不再受限於先前 preview 階段的存取限制。對於需要在 Cloudflare 邊緣網路上做低延遲文字擷取任務的開發者而言,多了一個可自行掌控成本與延遲的選項。
新舊比較：
  • 先前：Clairic 原本僅以 preview(封閉預覽)形式提供,Clairic-flash 尚未存在對外版本
  • 新在哪：Clairic 正式畢業為穩定版本,並新增輕量版 Clairic-flash,兩者皆以 open-weight 形式釋出於 Workers AI
  • 解決了什麼：開發者可自行下載、檢視、微調與自架部署模型權重,擺脫 preview 存取限制,並透過 flash 版本取得更低延遲/成本的擷取模型選項
8.【Engineering at Meta】Meta 如何用 AI Agent 把 ML 創新擴展到廣告排序模型群組
[2026-11-18] · Engineering at Meta
Meta 工程團隊發表系列文章的最新一篇,說明他們如何運用先前介紹過的「Ranking Engineer Agent(REA)」——一個能自主產生假設、設計實驗並驗證新機器學習技術的系統——把廣告排序模型的架構改進與訓練最佳化,有效率地推廣到 Meta 龐大且多樣的廣告排序模型群組中。過去這類跨模型的技術「平移」通常仰賴工程師逐一手動移植與驗證,在模型數量龐大且架構各異時極為耗時。透過讓 agent 自動執行平移與驗證流程,Meta 得以用更少人力把同一項改進套用到更多模型上,加速整體廣告系統的技術迭代速度,也是 Meta 近期一系列「AI agent 用於內部 ML 工程」文章的延伸。
新舊比較：
  • 先前：廣告排序模型的架構改進與訓練最佳化,過去需要工程師針對多個不同模型逐一手動移植與驗證,難以規模化
  • 新在哪：導入自主的 Ranking Engineer Agent(REA)系統,自動把已驗證的 ML 技術平移到 Meta 龐大且多樣的廣告排序模型群組
  • 解決了什麼：用更少的工程人力,把同一項 ML 改進更快速、更廣泛地套用到整個模型艦隊,加速技術迭代並降低規模化成本
評語：今天的報道呈現一個有趣的矛盾:幾乎每一則與「AI agent」相關的工程文章——GitHub 的 Agent Host Protocol、Meta 的 Ranking Engineer Agent、Mastra Factory——都在解決同一個更底層的問題:當程式碼審查、部署決策與維運判斷逐漸交給 agent 之後,「狀態該放在哪裡」與「誰該為結果負責」就變成比「模型能力」更急迫的工程課題,這也正是 Changelog 兩集節目(Quinn Slack 談 code review 正在消失、Socket CTO 談套件供應鏈失控)不約而同關切的焦慮。與此同時,Nginx 的未授權 RCE 與 KVM 的 MMU context 漏洞提醒我們,無論 agent 多先進,底層系統仍會因為最傳統的記憶體管理與輸入驗證疏失而被攻破——AI 工程的前沿敘事與基礎設施的老問題,其實是同時在發生、彼此脫節的兩條故事線。DaisyRose-27B 把 Terminal-Bench 成功率從 5.6% 推到 12% 的「進步」,放在這個脈絡下更顯諷刺:業界已經在認真討論把生產部署的決策權交給 agent,但衡量 agent 是否真的「懂」怎麼完成任務的基準測試,本身的通過率還不到六分之一。
